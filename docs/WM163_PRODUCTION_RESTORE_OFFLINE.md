## Important DrGrey finding

The recovered DrGrey application does not contain a hidden stock/production
restore workflow for Mini 3. Its Mini-3 flasher UI and dedicated Mini-3
flasher modules are explicitly service-firmware workflows. The unrelated
"restore" strings found elsewhere refer to calibration/eMMC backup restore.

Therefore a production restore must not be claimed as a recovered DrGrey
feature.

## Independently recovered generic updater grammar

Static reconstruction of drgrey.mini2style_flash recovers these payload
builders:

```text
REPORT SIZE:
  00
  <uint32_le total signed-file bytes>
  00 00 00 00 00 00 01 02

FILE START:
  01
  <uint32_le file size>
  <uint8 encoded_filename_length + 1>
  <UTF-8 filename>
  00 00 00 00

FILE DATA:
  02
  <uint32_le per-file chunk index>
  <chunk bytes>

FILE END:
  03
  <16-byte MD5 digest>

FINALIZE:
  17 zero bytes
```

For all chunk indices reached by the exact WM163 production archive, the
generic uint32 little-endian DATA index is byte-identical to the capture-backed
WM163 Session-B representation previously documented as uint24 little-endian
plus a zero byte.

The generic updater also describes post-verification installation progress
through push command 0x42. That differs from the WM163 Service-FW temporary
loader path, whose genuine capture ends with the special F7 B/FINALIZE
transition followed by commit probes until the temporary loader disappears.

## What the new hypothesis comparison proves

Run:

```powershell
py -3.14 analyze_wm163_restore_hypotheses.py
```

The script validates the exact production archive and then compares every
report-size, file-start, DATA, file-end and FINALIZE payload generated by:

1. the capture-backed WM163 Service-FW Session-B payload builders; and
2. the independently reconstructed DrGrey mini2style_flash builders.

A PASS means those payload grammars are byte-identical for the complete
production archive. It still does not prove the stock-restore destination
node, outer transfer command, FINALIZE response, or install/reboot state
machine.

## Remaining offline target

The next reverse-engineering target is the OUTER standard-upgrade
orchestration:

- exact transfer command used around the recovered file records;
- destination/node selection;
- sequence seeding and ACK policy;
- FINALIZE response semantics for a normal production install;
- interpretation of install-progress push 0x42;
- terminal success/reboot behavior;
- version/ARB policy around a Service-FW -> production transition.

Until those are recovered from independent binary/capture evidence, the GUI
Restore Production FW control must remain locked.
