# WM163 Production Restore — Offline Evidence

All work in this document is offline. The current project owner no longer has
the aircraft, so no conclusion below relies on a new hardware experiment.

## Evidence levels

| Subject | Level | What is actually proven |
| --- | --- | --- |
| WM163 V30 Service-FW Session A/B | CAPTURE-PROVEN | Genuine DrGrey USB capture, byte-for-byte generator parity, state-machine validation and offline live-path replay |
| Generic signed-file payload grammar | BINARY-RECOVERED | DrGrey mini2style_flash independently reconstructs the same report/start/data/end/finalize payload grammar |
| Exact WM163 v01.00.0500 archive in that grammar | STRUCTURALLY VALID | Exact archive validates and packetizes deterministically, including the 16-bit sequence rollover |
| WM163 stock-restore outer orchestration | UNPROVEN | No genuine stock-restore capture or separate DrGrey stock-restore worker has been recovered |

## Important DrGrey finding

Review of the recovered DrGrey package has **not identified an independently
verified Mini 3 stock/production-restore worker**. The named Mini-3 flasher
components and UI paths have service-firmware evidence, while other recovered
"restore" terms relate to calibration/eMMC backup restore.

The absence of a *named* stock-restore worker is not proof that generic
compiled code cannot be reused for production firmware. In particular,
`fetch_mini3_fw` and `_M3FlashWorker` must not be assumed to implement a
working WM163 stock-restore pipeline without an established call path and
capture/static behavioral evidence.

Therefore a production restore must not be claimed as a recovered DrGrey
feature, and the GUI restore control remains locked.

## Independently recovered generic updater grammar

Static reconstruction of drgrey.mini2style_flash recovers these payload
builders:

```text
REPORT SIZE:
  00
  <uint32_le total signed-file bytes>
  00 00 00 00 00 00 01 02

FILE START:
  01
  <uint32_le file size>
  <uint8 encoded_filename_length + 1>
  <UTF-8 filename>
  00 00 00 00

FILE DATA:
  02
  <uint32_le per-file chunk index>
  <chunk bytes>

FILE END:
  03
  <16-byte MD5 digest>

FINALIZE:
  17 zero bytes
```

For all chunk indices reached by the exact WM163 production archive, the
generic uint32 little-endian DATA index is byte-identical to the capture-backed
WM163 Session-B representation previously documented as uint24 little-endian
plus a zero byte.

The generic updater also describes post-verification installation progress
through push command 0x42. That differs from the WM163 Service-FW temporary
loader path, whose genuine capture ends with the special F7 B/FINALIZE
transition followed by commit probes until the temporary loader disappears.

## What the new hypothesis comparison proves

Run:

```powershell
py -3.14 analyze_wm163_restore_hypotheses.py
```

The script validates the exact production archive and then compares every
report-size, file-start, DATA, file-end and FINALIZE payload generated by:

1. the capture-backed WM163 Service-FW Session-B payload builders; and
2. the independently reconstructed DrGrey mini2style_flash builders.

A PASS means those payload grammars are byte-identical for the complete
production archive. It still does not prove the stock-restore destination
node, outer transfer command, FINALIZE response, or install/reboot state
machine.

## Remaining offline target

The next reverse-engineering target is the OUTER standard-upgrade
orchestration:

- exact transfer command used around the recovered file records;
- destination/node selection;
- sequence seeding and ACK policy;
- FINALIZE response semantics for a normal production install;
- interpretation of install-progress push 0x42;
- terminal success/reboot behavior;
- version/ARB policy around a Service-FW -> production transition.

Until those are recovered from independent binary/capture evidence, the GUI
Restore Production FW control must remain locked.

## Public generic upgrade-status messages (read-only)

Independent public reference: [o-gs/dji-firmware-tools DJI General 0x42 dissector](https://github.com/o-gs/dji-firmware-tools/blob/master/comm_dissector/wireshark/dji-dumlv1-general.lua).

The General command set `00/42` is labeled **Fw Upgrade Push Status**.
Its status payload (after DUML framing) has four documented states:

| First byte | State | Remaining fields |
| --- | --- | --- |
| `01` | Verify | None |
| `02` | UserConfirm | Time, reserved byte |
| `03` | Upgrading | Percent, packed 3-bit current index + 5-bit upgrade times |
| `04` | Complete | Completion reason, upgrade times |

Completion reasons 1–10 include success (1), failure (2), firmware error
(3), same version (4), cancellation (5), timeout (6), motor working (7),
firmware mismatch (8), illegal downgrade (9), and RC not connected (10).

`wm163_upgrade_status_offline.py` adds a **read-only payload decoder** and
`tests/test_wm163_upgrade_status_offline.py` adds synthetic, public-protocol
fixtures. Its `reports_success` field reports only the meaning of a parsed
generic status message; it cannot verify a WM163 restore or hardware outcome.

**Evidence: PUBLIC-PROTOCOL-CORROBORATED only.** No genuine WM163 stock
restore `00/42` capture was recovered; this does not establish a destination,
command sequence, ARB/rollback policy, FINALIZE ACK, or reboot protocol.
Production restore remains locked.
