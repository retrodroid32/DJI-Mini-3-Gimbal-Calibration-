## Session-A F5 narrowing

Static re-check after the first live A/VERIFY F5 has eliminated several
candidate causes.

### Loader bytes are not transformed

The compiled `drgrey.mini3_service_flash` constant table contains:

```text
session_a_loader.bin
72f7a3d3f40648c9e6c02583360c16b3
loader md5 does NOT match the capture — corrupt loader
```

and the native `load_loader()` path references ordinary filesystem operations:

```text
exists
abspath
dirname
join
open
read
```

No decompression/patch/decode transform is present in that loader-loading path.
The raw 743120-byte resource is therefore the intended Session-A loader input.

### A/DATA status handling matches DrGrey

The native flasher's recovered error text distinguishes:

```text
_ctrl   -> "<what>: rejected (...)"
_stream -> "stream stopped at ...: the drone did not ACK within ..."
```

This supports the earlier disassembly result that `_stream()` advances on a
matching response/sequence and does not apply the `_ctrl()` leading-status-byte
acceptance rule to each loader DATA ACK.

Therefore the first live implementation's choice not to reject A/DATA based on
payload[0] is not the identified cause of the final F5.

### Remaining material difference

DrGrey does not send service-flash packets by directly calling pyserial write.
Recovered `EngineTransport.xfer()` delegates to:

```python
transport.send_like_gray_flasher(
    pkt,
    wait_response=True,
    window_ms=timeout_ms,
)
```

The recovered transport module exposes serial-specific behavior and names
including:

```text
send_like_gray_flasher
send_and_collect
read_burst
reset_input_buffer
flush
write
write_timeout
monotonic
sleep
DRGREY_GRAY_RESET_AFTER / reset-after state
```

No evidence currently indicates it changes the DUML command contents. The
remaining target is to recover its exact serial pacing, input-buffer reset,
collection-window and post-write behavior and reproduce that behavior before
another Session-A attempt.

Live flashing remains blocked.


## Gray transport timing mismatch — confirmed

Offline execution of the real compiled CPython 3.14
`drgrey.transport.SerialTransport.send_like_gray_flasher()` against a fake
serial object proved the default production call order:

```text
reset_input_buffer()
write(packet)
(no flush)
(no post-write reset)
```

When four response bytes were injected immediately by the fake serial backend,
the compiled helper did:

```text
reset_input_buffer()
write(packet)
read(4)
return [b'....']
```

in approximately 0.1 ms. It did not wait for the remainder of the configured
response window after data became available.

By contrast, the first live recreation's response collector continued polling
until the entire drain/collection budget expired even after a matching ACK had
already arrived. With 759 Session-A DATA records and a 400 ms collection budget,
this could add roughly 300 seconds of unnecessary idle time to the loader
transfer.

This is a material transport/state-machine difference and is currently the
leading explanation for the observed pattern:

```text
all A/DATA records ACK
A/VERIFY -> F5
```

No standard public DJI definition for F5 in this exact Update Finish response
has been established. Do not assign a guessed meaning to it.

Live flashing remains blocked until the recreated transport returns immediately
on the first received burst and is offline-verified against the compiled
DrGrey helper.


## Gray transport equivalence — PASS

The recreated transport was compared offline against the actual compiled
CPython 3.14 DrGrey `SerialTransport.send_like_gray_flasher()` using the same
fake serial event.

Observed compiled DrGrey calls:

```text
reset_input_buffer
write
read(4)
```

Observed recreated calls:

```text
reset_input_buffer
write
read(4)
```

Both returned:

```text
[b'\xaa\xbb\xcc\xdd']
```

Comparison result:

```text
calls_equal=True
result_equal=True
EQUIVALENT
```

The four offline live-flash transport tests also passed under Python 3.14.

This removed two transport differences from the first failed Session-A
attempt, but a later genuine Dr.Grey USB capture proved additional protocol
mismatches in the reconstruction. Therefore transport equivalence alone is not
sufficient to authorize another live attempt.

The genuine capture established:

1. Session-A DATA uses a chunk index, not a byte offset.
2. Session-B DATA uses a per-file chunk index, not a byte offset.
3. Session B leaves one sequence number unused after each file START.
4. Genuine WM163 V30 B/FINALIZE is seq 0xFF8A, not 0xFF83.
5. Genuine A/VERIFY succeeds with status 00 when the loader is transferred
   with the captured semantics.

These findings strongly supersede the earlier theory that timing alone was the
leading explanation for F5.

Live flashing from this project is now hard-disabled until an offline-generated
trace matches the genuine capture for the full relevant transfer. See
`docs/WM163_DRGRAY_CAPTURE_FINDINGS.md`.

### Restore evidence gate

The following remain unproven for production restore and must not be assumed
from the Service-FW capture:

- whether the same Session-A loader is used to initiate production restore;
- whether Session B starts at the same destination/sequence seed;
- whether production B/FINALIZE accepts the same F7 transition;
- whether the same post-finalize loader/commit polling semantics apply;
- whether additional production-specific version/ARB/reboot steps occur.

Therefore the GUI **Restore Production FW** action remains disabled. The next
acceptable evidence is an independent known-good production-restore capture or
equivalent direct binary/runtime proof of the restore orchestration. The
offline candidate analyzers do not open a serial port and cannot write firmware.


## Single read-only live preflight (2026-10-07)

Before any future first Service-FW hardware-validation run, use the combined
read-only preflight:

```powershell
py -3.14 wm163_live_preflight.py --port COM23
```

The GUI exposes the same operation as **Run READ-ONLY Live Preflight**.

The preflight reuses only existing verified read paths and offline validators:

1. validates the exact local-only V30.00.0100 Service FW and Session-A loader;
2. validates the exact repo-local WM163 v01.00.0500 production archive;
3. reads the installed aircraft `cfg.sig` through the existing read-only
   General `0x00/0x4F` manifest probe;
4. passively listens for gimbal General `0x00/0xF1` diagnostics;
5. applies the WM163/V30 identity, FORMAL, ARB and diagnostic policy.

A valid combined-error state is explicitly allowed:

```text

  -> preflight may PASS
  -> Service FW / Advanced Calibration repairs 40011 first
  -> independent short 40021 repair follows afterward
```

A PASS does **not** enable or perform firmware flashing. Live Service-FW
flashing remains hard-disabled until a separate explicit first-hardware-test
decision is made.
